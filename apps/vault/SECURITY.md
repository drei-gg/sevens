# Storage format and security boundaries

Format version 2, development format. This documents the implementation; it is not a security audit or a promise of compatibility with future formats. Any format change must have explicit versioning and a tested migration before shipping to users. The byte-level specification is the "Format version 2" section of [`core/README.md`](core/README.md); this page summarizes it and the platform boundaries around it.

Both apps write version 2, so an iPhone vault or backup is the same files as an Android one. Version 1 is the iPhone's legacy format: still read, and migrated to version 2 (below).

## Key hierarchy

Each vault has a random **age X25519 identity** (`AGE-SECRET-KEY-1…`), its master key. Its public recipient (`age1…`) is in plain `header.json`; the identity is never stored unsealed. It is sealed twice, each time as a complete age file using age's **scrypt** passphrase recipient:

- `password`, under the unlock secret's key material: a passphrase of 12–4096 characters (at most 4096 UTF-8 bytes), an 8–32 ASCII-digit PIN, or an eight-dot-minimum 5×5 pattern. PIN and pattern inputs are versioned and type-prefixed before derivation (`Vault/PIN/v1/…`, `Vault/Pattern/5/v1/…`), pattern serialization includes crossed intermediate dots consistently, and the header names the credential kind so only that kind is tried.
- `recovery`, under a separate recovery key: 32 random bytes from the OS CSPRNG, shown as standard Base64.

New envelopes use scrypt log₂N = 17 with age's r = 8, p = 1 (128 MiB per attempt, OWASP's minimum for scrypt). Opening refuses a work factor above log₂N = 18 before doing any work, so a crafted backup cannot demand gigabytes of memory. Each envelope's plaintext starts with a context line (`Vault/password/v2/<UUID>` or `Vault/recovery/v2/<UUID>`); opening checks the context and that the identity matches the header's recipient, so an envelope moved from another vault or role is refused as damaged. Human-chosen credentials do not inherit the identity's entropy: short PINs and patterns remain guessable offline by anyone who has the vault files. Why scrypt rather than Argon2id is explained in the core README (age specifies scrypt; Argon2id would mean composing our own KDF and AEAD).

Changing the unlock method or secret replaces only `password`; a new recovery key replaces only `recovery`. The index and originals are untouched, and older backups keep the envelopes they were made with. The recovery key does not reconstruct lost files.

**Recovery key confirmation.** A recovery key is shown once: at creation, on replacement and after a version 1 migration. No readable copy is kept. Until the person confirms saving it, the encrypted index carries `recoveryUnconfirmed`. If the app locks or quits first, the key is gone from memory and the next unlock of that vault asks for a replacement (the normal replacement path) before the library opens. Opening the vault with that recovery key clears the flag, since the person evidently has it.

## Index and originals

- `index.age` is age-encrypted to the recipient. Its plaintext is a 32-byte HMAC-SHA256 tag, keyed by HKDF-SHA256 from the identity's secret with info `Vault/index-mac/v2/<UUID>`, followed by the library JSON. The tag is checked in constant time before anything is decoded. age provides confidentiality but not sender authentication and the recipient is public, so without the tag anyone able to write the vault directory or a backup could substitute an index that opens cleanly; only the identity can make the tag. The library's ID must match the header's.
- Each original is `<UUID>.age`, age-encrypted to the recipient and streamed in 64 KiB authenticated STREAM chunks with a final-chunk marker, so truncation and trailing data fail. Decryption also checks the plaintext's length and SHA-256 against the authenticated index, which binds every original to its entry.
- Vault names, filenames, types, lengths, digests, folders, dates, favorites, trash state, backup time and the recovery-confirmation and secret-change flags are inside `index.age`. `header.json` holds the format version, vault UUID, recipient, credential kind and the two envelopes. Directory count, ciphertext sizes and filesystem timestamps remain observable. Independent vaults provide separate access, not forensic deniability. A damaged envelope can prevent recovery through that credential even when the other remains usable.

Vault implements no cipher, KDF or MAC of its own: age (the `age` crate, an implementation of age-encryption.org/v1 tested against the reference implementation's vectors) and RustCrypto's HMAC, HKDF and SHA-2 do the cryptography.

## The shared core and what crosses into it

All version 2 cryptography, the credential rules, index coding and backup framing run once, in Vault's Rust core (`core/`), linked into each app in process through UniFFI. What the platform code hands it, and why:

- **Credentials:** the passphrase, PIN or pattern string and the recovery key, to validate them, build their key material and run scrypt for the envelopes (`header_v2_new`, `header_v2_open`, `header_v2_opens`, the rewrap functions).
- **The identity** stays inside the core as an opaque `VaultIdentity` object. Locking calls `wipe()`, which zeroizes the secret at once; an operation that began unlocked works on its own `fork()` and may finish committing encrypted data, but never repopulates a locked interface. Its one export, `export_for_custody()`, exists only so the platform can wrap it for biometric unlock.
- **Content:** originals stream through the core by path or descriptor for encryption and verified decryption; note text passes as bytes in memory (`data_encrypt`, `data_decrypt`, note search), so no plaintext note file is written; the decrypted index passes as a record for coding, sealing and validation.

Platform strings, byte buffers and framework objects carrying these values are not securely erased; the core zeroizes its own copies of the identity and of note text it encrypts. The platforms keep randomness for version 1 only, Keychain/Keystore custody, file protection and backup exclusion, directory staging, temporary-file cleanup, the session and lock lifecycle, backup delivery, pickers and the interface.

## Files and commits

Imports stream the source through the core, which measures its length and SHA-256 while encrypting to a staging name; the encrypted copy is then decrypted and verified before it is renamed and the index atomically replaced. The source is never deleted. Note edits create a replacement original before changing the index. Interrupted writes can leave unreachable encrypted files; they cannot make an incomplete import appear committed. Permanent deletion removes an index entry, then its encrypted file; this is ordinary filesystem deletion, not a flash-erasure guarantee. Backups and exported copies survive deletion.

Exports decrypt into a protected partial file and publish its final name only after whole-stream verification and the length/digest check. Previews, exports and thumbnails necessarily create temporary plaintext files; a thumbnail keeps only its downsampled image, in memory (on iOS in a bounded cache cleared on lock and on memory warnings). Notes and the index have explicit size limits (5 MB and 32 MB).

Owned storage and temporary directories use iOS complete file protection (Android: app-private, owner-only) and are excluded from OS backups. Temporary preview/export files are removed on dismissal, lock and next launch; removal at lock is best effort. Imported Photos/camera staging is removed after processing and on next launch. A receiving app controls any exported copies it receives.

## Backups

`.vault7` version 2 is transport framing around the vault's files: `7DVAULT2`, a big-endian UInt64 entry count, then per entry a UInt64 name length, the UTF-8 name, a UInt64 payload length and the payload. Entries are `header.json`, `index.age` and each `<UUID>.age`, byte for byte. Only those name forms are accepted; duplicates, traversal, unsupported magic, truncation, trailing bytes, oversized metadata and more than 1,000,000 entries are refused before anything further is written.

Restore extracts into an isolated staging directory, opens the supplied credential's envelope, authenticates the index, checks the entry names against it and verifies every original before moving the directory into place. An existing vault ID is never overwritten. A restore with a PIN, pattern or passphrase that already opens another vault on the device is refused (one secret opens one vault, as at creation and change); the recovery key restores it instead. A recovery-key restore cannot check the backup's own secret against other vaults, so it records `secretChangeRequired` in the restored index and the library stays closed (across locks and restarts) until the person sets a new PIN, pattern or passphrase, which gets the same duplicate check as any change. The framing itself is not separately authenticated; the index and every original are. Verification cannot establish freshness, prevent rollback to an older valid backup, or authenticate an unused envelope. Secret and recovery changes affect new backups; old backups retain their previous envelopes.

## Version 1 (legacy, iPhone only)

Vaults and backups made by earlier iPhone builds use version 1: a random 256-bit master key wrapped with PBKDF2-HMAC-SHA256 (600,000 iterations, 32-byte salts) and CryptoKit AES-GCM in `header.json`, an AES-GCM `index.sealed`, originals as Apple Encrypted Archive streams (`<UUID>.aea`, per-file keys from HKDF-SHA256) and `7DVAULT1` backups. The iPhone app still reads it with native CryptoKit and AppleArchive code. The first unlock with a vault's PIN, pattern or passphrase, or restoring a version 1 backup with one, migrates it: a new identity and envelopes; every original decrypted one at a time to protected temporary storage and re-encrypted by the core; the index sealed and read back; all in a staging directory published with two renames that `prepare` completes after a crash. A failure leaves the version 1 vault untouched and open. The version 1 recovery key cannot be carried over, so a new one is issued and must be confirmed (above). A vault opened by its recovery key or Face ID stays version 1 until then, and notes added to it are encrypted from memory too. Android refuses version 1 backups with a message to update the iPhone app.

## Automatic delivery

Snapshots are prepared with the unlocked vault, verified and then queued as ciphertext in separate app-owned storage. There are no background encryption credentials. The snapshot path is outside plaintext preview cleanup so an already-queued backup can finish after locking. The queue and destination bookmarks use complete-until-first-user-authentication protection and are excluded from OS backups. Failed or interrupted preparation is retried after the next unlock; startup removes uncommitted local preparation artifacts.

Provider filenames contain an opaque vault UUID and a revision hash of the encrypted header and index (SHA-256 over `header.json` then `index.age`). Provider folder names/bookmarks and copy timestamps exist outside the encrypted vault, so enabling cloud backup adds observable metadata. The provider can observe ciphertext sizes and versions. Old provider versions keep old envelopes; changing a secret is not remote revocation.

SevenBackup (Android: `AutomaticBackup`) obtains scoped directory access and coordinates streamed copy, hash comparison and final rename. It never deliberately overwrites a conflicting version. Retention removes only successful versions tracked by this queue after a newer copy is recorded. The provider controls subsequent remote upload. OS termination can leave an uncommitted provider-side partial file; cancellation normally removes it. Source code and tests cannot establish live provider durability or guarantee OS scheduling.

## Unlock and lifecycle

Optional biometric unlock is for one vault at a time. On iOS it stores the identity's custody export (for a version 1 vault, the master key) as a Keychain item with `whenPasscodeSetThisDeviceOnly` and `biometryCurrentSet`, requiring Face ID or Touch ID without a device-passcode fallback. Enabling it for a vault first deletes every other vault's item; turning it off deletes the stored vault's item whichever vault is open; launch removes items whose vault no longer exists. On Android, an AES-256-GCM Android Keystore key (StrongBox when present), usable only after a strong biometric and invalidated by a new enrollment, wraps the same export. Enrollment changes invalidate this convenience route; the independent credentials remain necessary.

The interface covers app windows whenever inactive and discards its session when the app is backgrounded or locked explicitly. On iOS, system pickers, the share sheet and Face ID run without backgrounding the app, so leaving Vault always locks it. On Android, a system screen Vault itself launched (document or photo picker, folder picker, share chooser, permission or biometric prompt) stops the activity; the lock waits for that flow, tracked from launch until its result or Vault's return and never longer than two minutes, while leaving any other way locks at once. Locking wipes the identity, then removes temporary plaintext and the in-memory thumbnail cache. Generation checks prevent an in-flight operation from reopening a locked interface. iOS does not block screenshots; Android sets FLAG_SECURE. Neither secures a compromised OS or stops an observer of an unlocked session.

## Release review

The core's suites cover the format's gates against the real encryption: byte preservation across chunks, wrong credentials and kinds, tampered, truncated and extended ciphertext, envelope swaps, forged indexes, interrupted writes, rotation without content change, identity wipe during long work, backup framing and the reference age vectors. The platform suites cover storage staging, restore without overwrite or duplicate secrets, recovery confirmation, migration from version 1 (iOS), lock cleanup and biometric custody. None of this replaces device tests, fault injection or an independent cryptographic and application review. No telemetry SDK, app account or app-operated backend is included. StoreKit and Google Play communicate with their platforms; choosing a provider or share destination invokes that provider's behavior.
